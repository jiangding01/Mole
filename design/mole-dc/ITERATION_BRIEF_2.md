## P1 · 清理确认页信息架构重设计（千级条目的真实规模）

### 问题（真机事实，非推测）

原型 `CLEAN_GROUPS` mock 约 129 项、每组十余条，平铺分组列表完全够用。真机一次真实扫描的分布是：

| 分组 | 条目数 | 其中 0B |
|---|---|---|
| Apps & utilities | 761 | 5 |
| Browsers | 492 | 0 |
| Developer tools | 349 | **177** |
| Application Support | 127 | 1 |
| App caches | 75 | 20 |
| User essentials | 45 | 22 |
| （其余段） | ~5 | 5 |
| **合计** | **1854** | **230（12%）** |

平铺后果（用户原话级反馈）：列表"很长很长不好查看"、没有排序、重点（GB 级大项）淹没在 0B 长尾里；复核 1854 行的确认页实质上不可复核——这反而削弱了信任承诺①"删之前看得见"。

### 需求

为确认页设计一个**在 500–2000 项规模下可复核**的信息架构。以下方向供你验证/推翻，不锁死：

1. **分组默认折叠为摘要卡**：组头 = 分组名 + `已选 X/Y` + `已选体积 / 总体积` + 展开箭头；点组头展开明细。整组勾选/反勾复选框保留在组头（与展开互相独立）。
2. **组内条目固定按体积降序**，0B 沉底。不提供排序切换控件（克制原则：体积降序是唯一正确默认，不值得一个 knob）。
3. **不做行聚合**（不把 45 条 Caches 并成一条"用户缓存"）：逐条路径可见是信任承诺①的粒度，聚合会把"看得见"降级成"看得见分类"。
4. 边界态要设计：单组 700+ 项展开后的滚动形态（展开即应看到该组 Top 大项）；整组全 0B 时的摘要卡形态；全部折叠时首屏应传达"总量 + 每组贡献"的一眼结论。

### 约束（实现侧不变量，设计不必迁就但不能违背）

- plan 粒度、item id、勾选语义、协议事件不变——这是纯展示层重构。
- 智能扫描页的结论卡不受影响（它已经是聚合形态）。
- "大小未知"行的既有呈现规则（CHANGELOG §1.2）在新形态下保留。

## P2 · "应用运行中"提示条（数据能力已就绪的部分）

官方 Mole Mac 的确认页顶部有一句"关闭 Bob、Chrome… 后可再清理 3.56 GB"——这是好交互。我们的数据能力与它不同，设计要贴我们的真实形态：

- **CLI 有的**：进程守卫（`mole_clean_process_guard`）在扫描时对"应用运行中"的目标**整段跳过或降级**，且知道是哪个进程挡的。
- **CLI 没有的**：被跳过目标的精确字节数（没扫它，所以没测量——诚实原则不允许编造"可再清理 X GB"）。

**需求**：设计一条确认页顶部的 info 级提示（非阻断、可关闭），措辞贴数据能力，例如："N 个分组因应用运行中被跳过 · 退出对应应用后重新扫描可纳入"，hover/展开列出具体应用名。**不要**承诺具体字节数。
