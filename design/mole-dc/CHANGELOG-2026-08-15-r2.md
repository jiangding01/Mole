## P1 · 清理确认页信息架构重设计(千级规模)

### 结论:采纳需求给的四个方向,一条未推翻

真机 1854 项 / 230 项 0 B 的分布已**按真实数字灌进设计稿**(不再是 129 项的玩具数据),`buildQuick()` 用固定种子的 mulberry32 生成,每次渲染结果一致:

| 分组 | 条目 | 其中 0 B |
|---|---|---|
| 应用与工具 | 761 | 5 |
| 浏览器 | 492 | 0 |
| 开发者工具 | 349 | 177 |
| 应用支持文件 | 127 | 1 |
| 应用缓存 | 75 | 20 |
| 用户基础项 | 45 | 22 |
| 其他片段 | 5 | 5 |
| **合计** | **1854** | **230** |

每组前 3–4 条是有名有姓的真实大项(Adobe 媒体缓存、Chrome 缓存、DerivedData、iPhone 备份…),其余为长尾片段(MB 级)。**总量约 34 GB**,与既有智能扫描结论量级自洽。

### 1. 分组默认折叠为摘要卡

组头信息密度按"一眼结论"设计:**整组复选框 · 图标 · 组名 · `已选 X / Y` · 贡献条 · `已选体积 / 总体积` · 展开箭头**。

- **贡献条**是本轮新增的关键元素:每组一条 3px 细条,宽度 = 该组体积 / 本 tab 最大组体积。全部折叠时,首屏一眼看出"应用与工具和开发者工具是大头,用户基础项无关紧要"——这正是需求方向 4 要的"总量 + 每组贡献"。
- 复选框与展开**互相独立**:点复选框只切勾选(`stopPropagation`),点组头其余区域才展开。
- 体积格式统一走 `fmtGB()`:≥1 GB 显示 `x.xx GB`,否则 `xxx MB`,零显示 `0 B`。长尾条目是 MB 级,用 GB 两位小数会全变 `0.00`,这是必须改的。

### 2. 组内固定按体积降序,0 B 沉底

`ensureClean()` 建组时一次性算好 `g._sorted`(体积降序,`size===0` 一律沉底),渲染只读不重排。**没有排序控件**——体积降序是唯一正确默认。

### 3. 展开后的滚动形态:首屏 12 项 + 渐进展开

单组 761 项一次性渲染会拖垮确认页,且违背"可复核"初衷。做法:

- 展开后**先渲染 Top 12**(必然是该组最大的 12 项,直接兑现"展开即见大项");
- 底部虚线按钮「再显示 50 项 · 还有 N 项」,点一次 +50;
- **未展开的组完全不构建条目 VM**——1854 项里只有当前展开组的可见部分进入渲染,页面始终轻。

### 4. 0 B 长尾的处理:分隔而不聚合

需求方向 3 明确禁止行聚合。因此 0 B 项**仍是逐条真实行**,只是:

- 排在全组最后;
- 第一条 0 B 行上方插入一条分隔线:「以下 177 项为 0 B · 空目录或已被系统清空」;
- 0 B 行整行 `opacity:.62`,尺寸列显示 `0 B`,hover 提示「目录为空或已被系统清空,删除不释放空间」。

这样"看得见"的粒度没有降级,重点又不会被 177 条空目录淹没。

**0 B 与「大小未知」是两回事,视觉上必须分得开**:`0 B` 是测量出来的零;`大小未知`(第一轮 §1.2 的规则原样保留)是测量超时。两者字号、字重、提示文案都不同。

### 5. 整组全 0 B 的摘要卡(边界态)

「其他片段」组 5 项全 0 B。摘要卡不显示贡献条,组名下方直接一行灰字「5 项 · 全部 0 B,无空间可释放」,体积列显示 `0 B / 0 B`。用户不必展开就知道这组可以跳过。

## P3 · 软件页扫描态:线性光谱条

结论:**不维持现状,但也不上光谱环**。

光谱环的叙事是"扫描 → 收束成结论",要分钟级时长才立得住;软件页是秒级,套环会让人还没看清就没了。定稿方案是把光谱环的**刻度词汇**降维成一条线:

- 64 根 2px 刻度横向排开,`tickWave` 关键帧让高度在 9px↔30px 之间起伏,按 `(i%16)` 分组错峰延迟 —— 读起来是同一种"仪器在采样"的语言,但没有起承转合;
- 上方 `READING APPLICATIONS` 微标签 + 下方「正在读取已安装应用与残留分布」;
- 下方保留原有骨架屏行(结构预告不变)。
- **纯 CSS 动画,不占 rAF**,秒级出现/消失不会有动画没跑完就被打断的尴尬。

## P4 · 卸载残留的预扫描三态

`_apps[].pre` 三个值,对应需求的三个状态:

1. **`done`** —— 行尾主题色徽标「6 项残留 · 1.2 GB」+ 勾号图标,hover「已预扫完成,展开即可逐项核对」。**展开前就知道有多少残留**,信息价值高于官方的"展开才知道"。
2. **`scanning`** —— 展开后顶部一条轻量等待行(spinner +「正在扫描残留…」),1.4 秒后自动转 `done` 并补上徽标。等待态只在展开时出现,不在列表里制造噪音。
3. **`failed`** —— **行上什么都不显示**,展开后走原有的按需扫描路径。静默回退,不打扰。

## P5 · 状态页「能耗」列 → 采纳方案 2(有依据的估算 + 标注)

- 列头改为 `能耗` + 一枚 `估算` 微标签,hover「由 CPU 时间换算的估算档位,非系统能耗读数」。
- 档位由 CPU 换算:`≥50% 很高` / `≥25% 高` / `≥10% 中` / 其余 `低`,并给档位配色(很高 `#E0745C`、高 `#D89A54`、中/低走文本灰阶),让这一列在扫视时能提供信息而不是一片同色文字。
- **不删列**的理由:进程表的价值是"谁在拖慢我的机器",CPU + 能耗档位是两个不同的视角(瞬时占用 vs 持续代价);删掉会让"持续高 CPU 告警"失去一个印证维度。**加标注**的理由:诚实原则——估算就说是估算。

## 实现侧提示

- 展示层重构,**plan 粒度、item id、勾选语义、协议事件全部未动**。
- `buildQuick()` / `QSPEC` / `VEND` / `KIND` / `rng()` 都是**设计稿造数据用的**,生产直接删——它们唯一的作用是让设计在真实规模下被验证过。要保留的是形态:折叠摘要卡 + 贡献条 + 体积降序 + 0 B 沉底与分隔 + 分页展开。
- 分页阈值(首屏 12 / 每次 +50)是设计稿取值,生产可按真实渲染性能调,但**首屏必须落在"能看到该组 Top 大项"这个区间**。

## 明确不做(沿用需求约定)

排序切换控件、搜索框、筛选器、行聚合、承诺被跳过目标的字节数、第一轮 P4 的四项(继续后置)。
